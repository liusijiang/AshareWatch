# 服务器端 A 股交易行情数据增量缓存、容错与多源备份技术方案

## 1. 方案背景与设计依据 (基于 TASK-000 实测结果)

在 **TASK-000** 预研与连通性实测中，我们在 Google AI Studio 运行环境中对全量外部行情接口进行了深度实测与边界摸底，获得了以下确凿的数据与事实依据：

1. **网络与协议选型定论**：
   - 云端沙箱容器（如 Google Cloud Run）受安全策略限制，**非 80/443 端口出站受限**，通达信原生 TCP:7709 二进制连接发生握手超时。
   - 结论：**服务端生产系统必须 100% 架构于标准的 HTTP/HTTPS 协议之上**。
2. **各数据源性能与质量基准**：
   - **腾讯财经批量接口 (`qt.gtimg.cn/q=...`)**：性能极佳，单次 HTTP 请求批量拼接 `/DOC/stockpool.json` 全池 66 只股票，耗时仅 **208ms**，GBK 转码 100% 正确，买卖五档、成交量额完整无乱码。
   - **腾讯历史复权 K 线 (`web.ifzq.gtimg.cn`)**：响应仅 **313ms**，前复权数据极其完整，适合作为首屏秒开通道。
   - **东方财富分时接口 (`push2.eastmoney.com/trends2`)**：单次返回当日完整 **241 根逐分数据及分时均价线**，但受跨洋网络抖动影响平均延时约 4.8 秒，适合作为冷启动与定时对齐通道，而不宜用于 2 秒级的高频轮询。
   - **新浪财经 (`hq.sinajs.cn`)**：注入 `Referer: https://finance.sina.com.cn` 后响应稳定在 **315ms**，且与腾讯源价格**交叉验证 100% 一致**，是极佳的热备通道。
   - **东方财富移动端基金接口 (`fundmobapi.eastmoney.com`)**：毫秒级返回公募基金净值与盘中实时估值，稳定性优于 Web 端 JS 接口。
3. **数据结构基准已锁定**：
   - 实测样本已固化保存在 [`/DOC/test_data_samples.json`](./test_data_samples.json)，本方案的所有缓存模型与字段映射均以此为权威基准。

### 熔断器状态机 (Circuit Breaker Pattern) 实现规范

每个数据源在内存中维护独立的状态控制器：
- **CLOSED (正常流通)**：所有请求流向主力源；失败计数器为 0。
- **OPEN (熔断阻断)**：连续失败达到 3 次，熔断器打开，强制将后续所有流量重定向至备用源，禁止向主力源发送高频流量；启动 60 秒倒计时冷却定时器。
- **HALF-OPEN (半开试探)**：冷却结束后，熔断器放行 1 次轻量心跳探针（如查询单只股票 `sh000001`）。若成功，状态自动复位至 CLOSED 并记录恢复日志；若依然失败，重新进入 OPEN 状态并延长冷却时间至 120 秒。

## 4. 服务端增量时序缓存引擎核心机制

基于 [`/DOC/test_data_samples.json`](./test_data_samples.json) 固化的数据格式，服务端在堆内存中构建三大核心时序缓存结构：

### 4.1 实时快照内存字典 (`TickSnapshotMap`)
* **结构载体**：Node.js 原生 `Map<string, UnifiedStockSnapshot>`，读写复杂度 $O(1)$，单次内存查询耗时 $< 0.05\text{ms}$。
* **数据契约定义**（严格匹配实测样本）：
  ```typescript
  interface UnifiedStockSnapshot {
    code: string;            // '300855'
    symbol: string;          // 'sz300855'
    name: string;            // '图南股份'
    price: number;           // 26.85 (最新成交价)
    preClose: number;        // 27.20 (昨收价)
    open: number;            // 27.10 (今开价)
    high: number;            // 27.45 (最高价)
    low: number;             // 26.60 (最低价)
    volume: number;          // 45210 (累计成交手)
    amount: number;          // 12185.3 (累计成交万元)
    change: number;          // -0.35
    changePercent: number;   // -1.29 (%)
    turnoverRate: number;    // 1.85 (%)
    pe: number;              // 32.4
    time: string;            // '20260925150000' (行情时间戳)
    bids: Array<{ price: number; volume: number }>; // 买一至买五
    asks: Array<{ price: number; volume: number }>; // 卖一至卖五
    afterHours?: {           // 科创/创业板盘后固定价格
      volume: number;        // 盘后成交股数
      amount: number;        // 盘后成交额
      dealCount: number;     // 盘后笔数
    };
    source: 'tencent' | 'sina'; // 标识当前数据来源
    updatedAt: number;       // 本地接收毫秒时间戳
    isStale: boolean;        // 是否为陈旧数据标识
  }
  ```

### 4.2 当日分时环形缓冲区 (`MinuteRingBuffer`) 与增量合成算法

A 股交易时间全天固定为 240 分钟（09:30~11:30 共 120 分钟，13:00~15:00 共 120 分钟，加开盘 09:30 点共 241/242 点）。

#### 内存定长数组模型：
每个活跃标的预分配一个长度为 242 的定长数组，每个元素结构如下：
```typescript
interface MinuteBarItem {
  minuteIndex: number;  // 0 ~ 241 (对应 09:30 至 15:00)
  timeStr: string;      // '09:31', '14:59' 等
  timestamp: number;    // 毫秒时间戳
  open: number;         // 该分钟开盘价
  close: number;        // 该分钟最新价/收盘价
  high: number;         // 该分钟最高价
  low: number;          // 该分钟最低价
  volume: number;       // 该分钟内独立成交量 (当前累计量 - 上一分钟累计量)
  amount: number;       // 该分钟内独立成交额 (当前累计额 - 上一分钟累计额)
  cumVolume: number;    // 当日截至该分钟的累计成交量
  cumAmount: number;    // 当日截至该分钟的累计成交额
  avgPrice: number;     // 分时均价 = (cumAmount * 10000) / (cumVolume * 100)
  isClosed: boolean;    // 该分钟是否已闭合
}
```

#### 2 秒级增量 Tick 合成算法逻辑：
1. **时间轴定位**：
   收到当前 Tick 时，根据当前服务器北京时间 $T$ 计算对应的 `minuteIndex`：
   - 09:30~11:30：$\text{index} = (Hour - 9) \times 60 + Minute - 30$；
   - 13:00~15:00：$\text{index} = 121 + (Hour - 13) \times 60 + Minute$。
2. **分钟内更新 (Intra-minute Update)**：
   - 若当前处于第 $i$ 分钟：
     - 若该 Bar 为刚开辟：设置 $\text{open} = \text{price}, \text{high} = \text{price}, \text{low} = \text{price}, \text{close} = \text{price}$；
     - 若该 Bar 已存在：更新 $\text{high} = \max(\text{high}, \text{price}), \text{low} = \min(\text{low}, \text{price}), \text{close} = \text{price}$；
     - 独立成交量计算：$\text{volume} = \max(0, \text{Tick.volume} - \text{lastClosedBar.cumVolume})$；
     - 均价计算：$\text{avgPrice} = \text{Tick.amount} / (\text{Tick.volume} \times 0.01)$。
3. **分针翻转闭合 (Minute Rollover)**：
   - 当系统时间步入下一分钟的第一笔 Tick 到达时，将上一分钟的 Bar 标记为 `isClosed = true`，固化其最终数据，并开辟新 Bar。
   - **此机制确保即使东财分时接口断网，系统也能完全依靠内部快照精准还原出符合交易所规范的分时图**。

### 4.3 磁盘持久化与动态烛线拼接器 (`Dynamic Bar Stitcher`)

为了避免重复拉取历史日 K 线造成流量浪费，系统采用 **静态文件持久化 + 盘中最后一根动态烛线** 的组合技术：

1. **静态持久化层**：
   - 本地磁盘路径：`./data/cache/klines/{code}_day_qfq.json`。
   - 存储截至前一交易日的完整历史日 K 线数据（如 500 根）。
   - 该文件在每日 15:35 盘后收盘时由定时任务统一更新一次，盘中处于只读状态。
2. **盘中动态烛线实时拼接 (Dynamic In-Flight Bar)**：
   - 当用户在前端请求日 K 线时，服务端读取磁盘中的前 499 根历史已闭合 K 线；
   - 服务端提取 `TickSnapshotMap` 中的最新快照，动态构造当日的第 500 根 Bar：
     `{ time: '2026-09-25', open: Tick.open, high: Tick.high, low: Tick.low, close: Tick.price, volume: Tick.volume }`；
   - 将该动态 Bar 追加至数组末尾返回给前端。
   - **收益**：全天日 K 线请求 100% 命中本地内存与磁盘，**外部 K 线接口调用量直接降至 0**！

## 5. 交易时段状态机与增量采集节流体系

为严格遵守第三方接口防爬风控红线（保持 QPS $\le 0.5$），系统实现精准的状态机调度：

```text
交易时段状态机 (CST = UTC+8):
[00:00~09:15] 休眠状态 (SLEEP)         --> 停止轮询，仅响应本地缓存
[09:15~09:25] 早盘竞价 (CALL_AUCTION)  --> 3秒/次 (提取虚拟撮合与未匹配量)
[09:25~09:30] 撮合静默 (PRE_MARKET)    --> 5秒/次 (锁定开盘第一笔大单)
[09:30~11:30] 连续竞价 (CONTINUOUS)    --> 2秒/次 (腾讯批量拼接整池，QPS=0.5)
[11:30~13:00] 午间休盘 (MID_BREAK)     --> 30秒/次 (心跳保活与增量校验)
[13:00~14:57] 连续竞价 (CONTINUOUS)    --> 2秒/次 (持续推流)
[14:57~15:00] 收盘竞价 (CLOSING)       --> 1秒/次 (锁定全天最终收盘价)
[15:05~15:30] 盘后固定 (POST_MARKET)   --> 5秒/次 (科创/创业板 f260~f264 字段轮询)
[15:35~24:00] 收盘归档 (ARCHIVED)      --> 执行1次日K归档并落盘，进入休眠
```

#### 超长批量拉取抗封控设计：
- 当前股票池包含 66 只股票，若单只轮询需要 66 个请求，极易触发封锁；
- 本方案采用腾讯接口的批量语法：`https://qt.gtimg.cn/q=sz300855,sh601606,sh688017,...`（全部 66 标的代码通过逗号串接）；
- **全池刷新只需 1 次 HTTP 请求**，网络开销仅 15KB，耗时约 200ms。交易时段 2 秒轮询一次，实际外部调用频率仅为 **0.5 次/秒**，处于绝对安全阈值之内。

## 6. 异常数据清洗与脏数据防御机制

金融数据在网络抖动或源端异常时可能出现极端脏数据，进入缓存前必须执行清洗过滤：

1. **价格合理性边界校验 (Price Band Sanitization)**：
   - 检查新报价是否超出 A 股涨跌停限制（主板 $\pm10\%$，科创/创业板 $\pm20\%$，ST $\pm5\%$）；
   - 若 $|\text{Tick.price} - \text{preClose}| / \text{preClose} > 0.21$（非新股上市首日），判定为源端脏数据，**丢弃该异常价格并沿用上一有效价**。
2. **极值逻辑自洽校验**：
   - 强制断言：$\text{high} \ge \max(\text{open}, \text{close}, \text{low})$ 且 $\text{low} \le \min(\text{open}, \text{close}, \text{high})$；
   - 若成交量出现倒退（当前累计 volume < 上一帧 volume），忽略量额更新，保留原有值。
3. **陈旧数据时间戳检测 (Stale Tick Detection)**：
   - 对比 Tick 报文内的时间戳与服务器当前时间，若超过 30 秒无更新（且当前处于连续竞价时段），系统向前端下发 `isStale: true` 标记，界面提示“行情源可能存在延迟”，避免误导决策。

## 7. 前端增量同步与通信协议规范 (SSE Diff Stream)

为大幅节约前端渲染负载与 WebSocket/SSE 网络带宽，服务端禁止全量广播，统一采用 **增量差分（Diff Patch）** 下发：

### 7.1 接口契约定义

#### 1. 全量初始化接口 (首屏冷加载)
* `GET /api/stock/full-state?code=sz300855`
  * 返回：全量盘口快照 + 当日 241 根分时数组 + 最近 100 根历史日 K 线（100% 内存/磁盘直出，耗时 $\le 5\text{ms}$）。

#### 2. SSE 增量推流接口 (盘中动态流)
* `GET /api/realtime/stream`
* **广播策略**：
  * **高频轻量广播 (`event: tick_diff`)**：每 2 秒下发一次，仅包含价格跳变的标的，且仅下发有变动的字段（如 `{ code: '300855', price: 26.86, changePercent: -1.25, vol: 45220 }`），体积缩减 85%！
  * **分钟 Bar 封盘事件 (`event: minute_bar`)**：每到第 00 秒分针翻转时下发最新闭合的 1 分钟 Bar，前端图表组件直接调用 `chart.update()` 追加单点，无重绘抖动。
  * **系统事件 (`event: sys_status`)**：广播数据源切换、交易时段切换或网络熔断通知。
